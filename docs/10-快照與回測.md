# 10 · 每日快照與回測

> **English summary**
> A daily snapshot freezes today's scores and heat levels into an immutable file. Without it, a
> backtest would use today's data to "predict" the past — a look-ahead bias. With two or more
> snapshots, `scripts/backtest.mjs` can answer the real question: *did last month's scores predict
> this month's heat change?* It reports Spearman ρ, Precision@10%, Lift@10% and the high-vs-low
> score group difference in log heat growth. Snapshots are slim (~150 KB/day) and committed by a
> free GitHub Actions job.

## 中文

### 1. 每日快照是什麼

每天把「**當天的分數 + 當天的熱度**」存成一個不可變檔案：

```
data/snapshots/2026-11-16.json
{
  "date": "2026-11-16",
  "modelVersion": "breakout-0.1",
  "items": [
    { "id": "anilist-21", "medium": "anime", "hitScore": 89.3, "dims": {...}, "heat": 770120 },
    ...
  ]
}
```

它只存回測需要的欄位（分數、五維、熱度代理），約 150 KB／天。

### 2. 為什麼不能「拿上個月的資料套模型、比對這個月」？

**可以，而且這正是正確做法**——但前提是你要有「上個月當時的分數」，而不是用今天的模型回頭算上個月。

- 如果今天用最新資料重算「上個月」，你會用到上個月之後才發生的資訊（例如某部劇後來的爆紅），這叫**前視偏差（look-ahead bias）**，回測結果會虛高。
- 快照的作用就是保留「當時已知的狀態」。回測時：**t0 的分數 → 預測 t1 的熱度變化**，中間不允許使用 t1 的資訊。

### 3. 回測怎麼跑

```bash
node scripts/snapshot.mjs                    # 今天存一份
# ... 7–30 天後再跑一次，或從 git 歷史取舊快照
node scripts/backtest.mjs                    # 自動用最後兩份快照
node scripts/backtest.mjs 2026-11-16 2026-12-16   # 指定日期
```

輸出：

| 指標 | 意思 | 判讀 |
|---|---|---|
| Spearman ρ | 分數排名 vs 熱度成長排名的相關 | > 0.2 才有初步訊號 |
| Precision@10% | 分數前 10% 的作品，有多少真的進入熱度成長前 10% | 越高越好 |
| Lift@10% | Precision@10% ÷ 隨機基準（10%） | > 1.5 才算有用 |
| Mean Δheat | 高分組 vs 低分組的平均對數成長差 | 正值代表高分組成長更快 |

### 4. 快照還能回答什麼

1. **模型是否真的有預測力**（不是自我驗證）。
2. **哪一維最有預測力**：分別用 reach／quality／buzz／momentum／crossover 做單維回測，比較 ρ。
3. **「上升最快」榜單**：兩份快照相減，就是這段期間的熱度成長榜——這是「正在爆」比靜態總量更有價值的版本。
4. **模型改版驗證**：v0.2 上線後，用同一段歷史快照比較新舊模型的 ρ / Lift。

### 4.5 自動化

- **每日 09:00（台北）**：`snapshot.yml` 自動抓取、重建、存快照並 commit。
- **每週一 11:00（台北）**：`backtest.yml` 自動跑回測，結果寫進 GitHub Actions 的 job summary。
- 兩者皆為公開 repo 免費額度；不需要任何金鑰。

### 5. 限制

- 快照間隔太短（< 7 天）時，熱度變化多為雜訊；建議 7–30 天。
- 外部可見的「熱度」是代理指標（AniList popularity、Bangumi collect），不是平台後台數據。
- 需要累積 6–12 個月、至少 6 份快照，結論才穩定。

## English (full version)

### 1. What a daily snapshot is

Every day the pipeline freezes **today's scores plus today's heat** into an immutable file under `data/snapshots/YYYY-MM-DD.json`. It stores only what a backtest needs — hit score, five dimensions, and a heat proxy — roughly 150 KB per day.

### 2. Why you cannot just re-run the model on last month's data

You can — and you should — but only if you use **the scores as they were computed at that time**. Recomputing last month with today's data leaks information that did not exist yet (a title's later breakout, for example). That is **look-ahead bias**, and it inflates backtest results. The snapshot exists to preserve the "known at the time" state: score at t0 predicts heat change to t1, with no t1 information used.

### 3. Running a backtest

```bash
node scripts/snapshot.mjs
# wait 7–30 days (or pull an older snapshot from git history)
node scripts/backtest.mjs
node scripts/backtest.mjs 2026-11-16 2026-12-16
```

Outputs: Spearman ρ between score rank and heat-growth rank, Precision@10%, Lift@10% (precision ÷ 10% random baseline), and the high-vs-low score group difference in mean log heat growth. A useful signal looks like ρ > 0.2 and Lift@10% > 1.5.

### 4. What else snapshots enable

Out-of-time model validation; per-dimension predictive power (which dimension predicts best); a genuine "rising fastest" chart (difference of two snapshots) instead of a static total; and A/B comparison of model versions on the same history.

### 5. Limits

Intervals under 7 days are mostly noise — prefer 7–30 days. External heat is a proxy (AniList popularity, Bangumi collections), not platform-internal data. Six to twelve months of snapshots are needed before conclusions stabilise.
