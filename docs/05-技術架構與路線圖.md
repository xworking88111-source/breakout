# 05 · 技術架構與路線圖

> **English summary**
> The MVP is a static Vite + React + TypeScript app with hand-written SVG charts, deployed to GitHub
> Pages for free, plus a pure-Node data pipeline that refreshes a public AniList snapshot weekly via
> GitHub Actions. There is no database, no server, no paid service and no API key. The document
> covers the stack choice and rejected alternatives, the data model, the free deployment path, a
> 12-week roadmap, and the upgrade path (Supabase free tier + DuckDB) if the project grows.
> Estimated running cost: **US$0/month**.

## 中文

### 1. 技術選型（全免費）

| 層 | 選擇 | 為什麼 | 被否決的選項 |
|---|---|---|---|
| 前端 | **Vite + React 19 + TypeScript** | 靜態建置、生態成熟、型別安全 | Next.js（MVP 不需要 SSR／API route，反而增加部署複雜度） |
| 樣式 | **原生 CSS + 設計變數** | 零依賴、可控、載入快 | Tailwind（多一層建置與 class 噪音） |
| 圖表 | **手寫 SVG**（雷達、瀑布、折線、直方圖） | 無授權問題、檔案小、完全可控 | Recharts／ECharts（bundle 大、樣式難統一） |
| 路由 | **Hash routing** | 靜態托管零設定、不需 404 fallback | React Router + rewrite 規則 |
| 資料 | **靜態 JSON**（`works.json`） | 可 commit、可 diff、可重現 | 資料庫（MVP 無此需求） |
| 資料管線 | **純 Node 腳本** | 無框架、易審核 | Airflow／dbt（過重） |
| 排程 | **GitHub Actions cron** | 公開 repo 免費 | 自架 cron（要維護機器） |
| 托管 | **GitHub Pages** | 免費、CDN、與 repo 整合 | Vercel／Netlify（免費層夠用但多一個帳號依賴） |
| CI | **GitHub Actions** | 同排程 | 第三方 CI |
| 監控 | **validator + CI 紅灯** | 零成本 | Sentry 等（MVP 不需要） |

**成本**：0 元／月（公開 repo 的 Pages 與 Actions 皆免費）。

### 2. 系統架構

```
┌──────────────────────── GitHub Actions（每週一 02:00 UTC）────────────────────────┐
│  fetch_anilist.mjs → anime.json → build_dataset.mjs → works.json → validate        │
│                              │ commit & push                                       │
└──────────────────────────────┼─────────────────────────────────────────────────────┘
                               ▼
┌──────────────────── GitHub Pages（免費 CDN）────────────────────┐
│  app/dist  ←  vite build（BASE_PATH=/<repo>/）                   │
│  純靜態：HTML + JS + CSS + JSON，無後端、無追蹤、無 cookie         │
└─────────────────────────────────────────────────────────────────┘
```

- 前端直接 `import` `works.json`，build 時打包，執行時零 API 呼叫。
- 沒有使用者資料，因此沒有隱私合規負擔（無 cookie、無 analytics）。
- 若要加 analytics，建議用隱私友善、免費的方案（如 Cloudflare Web Analytics），並在隱私頁說明。

### 3. 資料模型（MVP）

```ts
Work {
  id, medium, title{zh,en,native}, year, region, platform,
  genres[], tags[{zh,en}], episodes?, episodeMinutes?,
  synopsis{zh,en},
  dims{reach,quality,buzz,momentum,crossover},
  hitScore, contributions[], ci[2], confidence,
  heatCurve?[12], scoreDistribution?[],
  drivers[{text{zh,en}, source?}],
  provenance{status, sources[], note{zh,en}}
}
```

完整欄位定義與資料狀態規則見 [02-量化評分機制 §4](02-量化評分機制.md)。

### 4. 免費部署步驟

1. 建立公開 repo，push `main`。
2. Settings → Pages → Source: **GitHub Actions**。
3. `deploy.yml` 自動 build + deploy。
4. 網址：`https://<user>.github.io/<repo>/`。
5. 根網域（`<user>.github.io`）則把 `BASE_PATH` 改為 `/`。

### 5. 12 週路線圖

| 週 | 里程碑 | 驗收標準 |
|---|---|---|
| 1–2 | Repo 上線、Pages 部署、CI 綠燈 | 網站可公開瀏覽、每週自動更新 |
| 3–4 | 短劇擴充到 100 部 | 每筆有來源、狀態標記、validator 通過 |
| 5–6 | 動漫擴充到 500 部、Bangumi 交叉驗證 | 資料狀態與偏差說明更新 |
| 7–8 | 排行榜進階（多選篩選、儲存視圖、比較分享連結） | URL 可分享、可匯出 |
| 9–10 | 英文內容補齊、SEO（hreflang、sitemap、OG） | 英文頁可被搜尋索引 |
| 11–12 | 研究者模式（API 靜態 JSON、引用、快照） | 可下載、可引用、有版本號 |

### 6. 升級路徑（不是現在）

| 觸發條件 | 升級 |
|---|---|
| 作品 > 5,000 筆或需要歷史時序 | DuckDB（本機分析）+ Parquet 快照 |
| 需要使用者收藏／提醒 | Supabase 免費層（Postgres + Auth） |
| 需要每日更新 | GitHub Actions 改為每日（仍免費） |
| API 對外服務 | Cloudflare Workers 免費層 + 快取 |

### 7. 風險與技術債

1. **資料量**：靜態 JSON 在 5,000 筆以內仍可接受（gzip 後約數百 KB）。
2. **建置依賴**：AniList 若改條款，需改用備援（Jikan／Bangumi）。
3. **單點排程**：GitHub Actions 偶有延遲；失敗不影響現有網站（舊資料仍在）。
4. **無後端**：無法做個人化；Phase 2 再處理。
5. **i18n**：目前字典是手寫 TS；規模變大後可改 JSON + 翻譯流程。

## English (full version)

### 1. Stack (all free)

Vite + React 19 + TypeScript for the frontend; hand-written CSS design tokens; hand-written SVG charts (radar, waterfall, sparkline, histogram) to avoid library weight and licensing issues; hash routing for zero-config static hosting; static JSON as the dataset; pure Node scripts for the pipeline; GitHub Actions for CI and weekly refresh; GitHub Pages for hosting. Rejected: Next.js (no SSR need), Tailwind (extra build layer), Recharts/ECharts (bundle size), React Router rewrites, Airflow/dbt (overkill), databases (not needed for the MVP). **Running cost: US$0/month.**

### 2. Architecture

A weekly GitHub Actions job fetches the AniList snapshot, rebuilds and validates the dataset, and commits it; the commit triggers a Vite build deployed to GitHub Pages. The site is pure static HTML/JS/CSS/JSON — no backend, no tracking, no cookies. `works.json` is imported at build time, so there are zero runtime API calls.

### 3. Data model

See the `Work` interface summary above and the full data dictionary in docs/02 §4.

### 4. Free deployment

Create a public repo → push `main` → Settings → Pages → Source: GitHub Actions. The workflow builds and deploys to `https://<user>.github.io/<repo>/`; set `BASE_PATH=/` for a root site.

### 5. 12-week roadmap

Weeks 1–2: repo, Pages, CI. 3–4: 100 short dramas. 5–6: 500 anime + Bangumi cross-check. 7–8: advanced charts, saved views, shareable comparisons. 9–10: full English content, hreflang, sitemap, OG. 11–12: researcher mode (static API, citation, snapshots).

### 6. Upgrade path (not now)

DuckDB + Parquet beyond 5,000 titles or when historical time series are needed; Supabase free tier for accounts and watchlists; Cloudflare Workers free tier if a public API is needed.

### 7. Risks and technical debt

Static JSON is fine up to ~5,000 records (a few hundred KB gzipped); AniList terms could change (fallback: Jikan/Bangumi); GitHub Actions scheduling can drift (the live site keeps serving the last good snapshot); no personalisation without a backend; the hand-written i18n dictionary should migrate to JSON when it grows.

## 8. 需不需要連接資料庫？會提高效能嗎？

**MVP 與 1,000 部規模：不需要，而且資料庫不會讓網站變快。**

### 8.1 為什麼不需要

| 面向 | 靜態 JSON（現況） | 資料庫（例如 Postgres） |
|---|---|---|
| 讀取延遲 | GitHub Pages CDN，全球邊緣節點直接回檔案 | 需要伺服器 → 多一跳網路 + 查詢時間 |
| 成本 | 0 元 | 免費層有限（Supabase 500 MB / 月流量限制） |
| 維運 | 無 | 連線池、備份、遷移、監控 |
| 快取 | 瀏覽器 + CDN 自動快取 | 需要額外快取層（Redis）才追得上 |
| 1,088 部資料量 | 1.9 MB / gzip 282 KB，解析 8 ms | 查詢反而更慢 |

**結論**：這個產品的資料是「**少量、唯讀、每日更新一次**」，屬於典型的靜態資料集。CDN + JSON 是最快也最便宜的做法。

### 8.2 什麼時候才需要資料庫

| 觸發條件 | 建議方案（皆免費起步） |
|---|---|
| 想做「歷史時序」（每日快照、趨勢圖） | 先把每日 JSON 存成 `data/snapshots/YYYY-MM-DD.json`，用 DuckDB 在本機／CI 分析；超過 1 年再考慮物件儲存 |
| 需要使用者帳號、收藏、提醒 | Supabase 免費層（Postgres + Auth + Row Level Security） |
| 需要公開 API（依查詢參數回傳） | Cloudflare Workers 免費層 + KV / R2，或 GitHub Pages 上的預生成 JSON 分片 |
| 需要即時榜單（分鐘級） | 才需要真正的後端 + 資料庫 + 排程 |

### 8.3 建議的演進順序

```
Phase 1（現在）：靜態 JSON + GitHub Pages + 每週 Actions    成本 0
Phase 2：每日快照（純檔案）+ DuckDB 分析                    成本 0
Phase 3：Supabase 免費層（帳號 / 收藏 / 提醒）              成本 0（用量內）
Phase 4：Cloudflare Workers API + 快取                      成本 0（用量內）
```

> 一句話：**先不要把「資料庫」當成效能問題的解方**。這個網站的效能來自 CDN 與靜態化；資料庫的價值在「寫入、關聯查詢、使用者資料」，不是「讓頁面變快」。

### 8. Do we need a database? Will it improve performance?

**For the MVP and even at 1,000+ titles: no — and a database would not make the site faster.**

| Dimension | Static JSON (current) | Database (e.g. Postgres) |
|---|---|---|
| Read latency | GitHub Pages CDN, served at the edge | Extra network hop plus query time |
| Cost | $0 | Free tiers have storage and traffic caps |
| Operations | None | Connection pooling, backups, migrations, monitoring |
| Caching | Browser + CDN for free | Needs an extra cache layer to compete |
| 1,242 titles | 2.1 MB / 309 KB gzipped, ~8 ms parse | Slower for this access pattern |

The product's data is **small, read-only and refreshed at most daily** — a classic static dataset. CDN + JSON is both the fastest and the cheapest option.

**When a database becomes worth it**: historical time series (store daily JSON snapshots and analyse with DuckDB first); user accounts, watchlists and alerts (Supabase free tier); a public API (Cloudflare Workers free tier plus KV/R2); minute-level live charts (only then do you need a real backend and database).

**Recommended sequence**: Phase 1 static JSON + Pages + weekly Actions ($0) → Phase 2 daily snapshots + DuckDB ($0) → Phase 3 Supabase free tier for accounts ($0 within quota) → Phase 4 Workers API + cache ($0 within quota).

> In short: **do not treat "a database" as the answer to a performance question.** This site's speed comes from static rendering and a CDN; a database earns its place through writes, relational queries and user data — not by making pages load faster.
